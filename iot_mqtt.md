## 1. Overview

### 1.1 Why MQTT?

The legacy HTTP API required the device to establish a full TCP + TLS handshake on every request. There was no persistent connection, so the server had no way to detect when a device lost power or went offline. Stop events were fire-and-forget — if a request failed, the device had to implement its own retry logic via `saveOfflineData`.

MQTT solves all of these problems:

| Concern | HTTP (legacy) | MQTT (new) |
|---------|--------------|-----------|
| Connection overhead | Full handshake per request | One CONNECT, then persistent |
| Offline message delivery | Device must implement retry | QoS 1: broker queues and retries |
| Abnormal disconnect detection | Server never knows | Last Will and Testament (LWT) |
| Bandwidth per message | ~500+ bytes (HTTP headers) | 2–10 bytes fixed header |
| Auth | Per-request token or email body field | Once at CONNECT time |
| Real-time dashboard | Dashboard must poll REST endpoints | Server pushes via WebSocket on each event |

The Last Will and Testament feature alone justifies the migration: when a device loses power mid-stop, the broker automatically publishes a `connected: false` message to the `status` topic within seconds, triggering an immediate dashboard update without any polling.

### 1.2 Architecture

```
  ┌─────────────────────────────────────┐
  │        Factory Floor                 │
  │  ┌────────────┐  ┌────────────┐     │
  │  │ Raspberry  │  │ Raspberry  │ ... │
  │  │  Pi Unit A │  │  Pi Unit B │     │
  │  └─────┬──────┘  └─────┬──────┘     │
  └────────┼───────────────┼────────────┘
           │ MQTT over TLS (port 8883)
  ┌────────▼───────────────▼────────────┐
  │       Mosquitto MQTT Broker          │
  │  • Per-device ACLs                  │
  │  • QoS 1 persistent sessions        │
  │  • Last Will and Testament          │
  └──────────────────┬──────────────────┘
                     │ MQTT subscribe (fp/v1/#)
  ┌──────────────────▼──────────────────┐
  │         Express.js Backend           │
  │  • MQTT subscriber                  │
  │  • HTTP REST API (preserved)        │
  │  • Socket.io server                 │
  └────────┬──────────────┬─────────────┘
           │              │
    PostgreSQL       Socket.io events
  (tenant schemas)        │
                   ┌──────▼──────────────┐
                   │  Next.js Dashboard   │
                   │  (live updates)      │
                   └─────────────────────┘
```

Each device publishes to topics prefixed `fp/v1/{companyId}/machine/{machineId}/`. The `companyId` is the company's integer ID — the same number used as the PostgreSQL schema suffix (`tenant_{companyId}`). The backend extracts it from the topic path to route each message to the correct tenant database.

### 1.3 Prerequisites

Before a device can connect to MQTT, you need:

- **Broker URL** — provided by your deployment (e.g., `mqtt://localhost:1883` for dev, `mqtts://mqtt.fpanalyzer.com:8883` for production).
- **Device credentials** — a unique `username` and `password` generated by the provisioning endpoint (see section 10).
- **TLS CA certificate** — required for production (`mqtts://`); the CA certificate used by the broker.
- **`machineId`** — the integer ID from the `machines` table. New devices obtain this via the enrollment flow (section 4.1).
- **`companyId`** — your company's integer ID. Baked into the MQTT username at provisioning.

## 2. MQTT Connection Details

### 2.1 Broker URLs

| Environment | URL | TLS |
|-------------|-----|-----|
| Development (local Docker) | `mqtt://localhost:1883` | No |
| Production | `mqtts://mqtt.fpanalyzer.com:8883` | Yes (required) |

The exact production URL is returned by the provisioning endpoint in the `brokerUrl` field.

### 2.2 Authentication

Each device is provisioned with a unique username and password. These replace the legacy `company_email_id` body-field mechanism.

**Username format:** `machine-{companyId}-{machineId}`
**Example:** `machine-5-9` (companyId=5, machineId=9)

Credentials are generated server-side via the provisioning endpoint:

```
POST /api/v1/admin/iot/units/{machineId}/provision-mqtt
Authorization: Bearer <admin JWT>
```

**Response:**
```json
{
  "success": true,
  "data": {
    "machineId": 9,
    "username": "machine-5-9",
    "clientId": "machine-5-9",
    "password": "w3rT9...base64url...Kj2P",
    "brokerUrl": "mqtts://mqtt.fpanalyzer.com:8883",
    "aclTopicPrefix": "fp/v1/5/machine/9/#",
    "provisionedAt": "2026-05-20T10:00:00.000Z",
    "note": "Store the password securely — it will not be shown again."
  }
}
```

**The password is shown once and never stored by the server.** Write it to the device's persistent config immediately.

### 2.3 Client ID

Use the provisioned `clientId` value exactly. It is the same string as `username`: `machine-{companyId}-{machineId}`.

If you use a different client ID, the broker's ACL rules will reject the connection.

### 2.4 Session Configuration

| Parameter | Value | Reason |
|-----------|-------|--------|
| `clean_session` | `false` | Enables persistent sessions so the broker queues messages while the device is offline |
| `keepalive` | `60` (seconds) | Broker detects disconnects within 1.5× keepalive (90 s) |
| `reconnect_period` | `5000` (ms) | Reasonable re-connect delay |
| `connect_timeout` | `30000` (ms) | Allows for slow factory Wi-Fi |

### 2.5 Last Will and Testament (LWT)

Set the LWT on the `CONNECT` packet — before the connection is established. If the device disconnects without sending a DISCONNECT packet (e.g., power failure), the broker automatically publishes this message to the `status` topic.

| Parameter | Value |
|-----------|-------|
| Topic | `fp/v1/{companyId}/machine/{machineId}/status` |
| Payload | `{"machine_id":{machineId},"connected":false,"reason":"lwt","ts":0}` |
| QoS | `1` |
| Retain | `true` |

**Use `ts: 0` in the LWT payload.** The server rejects messages with timestamps more than 60 seconds old. Since the LWT is set at connect time but fired by the broker potentially hours later, a real timestamp would be stale. The value `0` (falsy) bypasses the staleness check on the server side.

### 2.6 TLS Configuration (Production)

```python
import ssl

tls_context = ssl.create_default_context()
tls_context.load_verify_locations(cafile="/path/to/ca.crt")

client.tls_set_context(tls_context)
```

Validate the broker's server certificate (`check_hostname=True`, `verify_mode=ssl.CERT_REQUIRED`). Do not disable certificate validation in production.

## 3. Topic Specification

### 3.1 Topic Notation

- `{companyId}` — your company's integer ID (e.g., `5`)
- `{machineId}` — the machine's integer ID from the `machines` table (e.g., `9`)
- `new` — literal string used during enrollment when the device has no `machineId` yet

### 3.2 Device → Server Topics

| Topic | Purpose | QoS | Retain | Replaces HTTP endpoint |
|-------|---------|-----|--------|------------------------|
| `fp/v1/{companyId}/machine/{machineId}/heartbeat` | Periodic online signal | 1 | Yes | `installV1` (heartbeat path) |
| `fp/v1/{companyId}/machine/{machineId}/stop/start` | Machine stopped — open a stop record | 1 | No | `saveStopDataV1` |
| `fp/v1/{companyId}/machine/{machineId}/stop/end` | Machine restarted — close the stop record | 1 | No | `installV1` (restart path) |
| `fp/v1/{companyId}/machine/new/enroll` | First-boot enrollment — request a `machineId` | 1 | No | `installV1` (new unit path) |
| `fp/v1/{companyId}/machine/{machineId}/stop/replay` | Bulk replay of offline-buffered stops | 1 | No | `saveOfflineData` |
| `fp/v1/{companyId}/machine/{machineId}/firmware/check` | Check for firmware update | 0 | No | `checkIotLatestVersion` (optional) |
| `fp/v1/{companyId}/machine/{machineId}/status` | LWT + manual online/offline signal | 1 | Yes | (new — no HTTP equivalent) |

### 3.3 Server → Device Topics

| Topic | Purpose |
|-------|---------|
| `fp/v1/{companyId}/machine/new/enrolled` | Response to enroll — contains assigned `machineId` |
| `fp/v1/{companyId}/machine/{machineId}/stop/replay/ack` | Acknowledgement of replay batch with `committed` count |
| `fp/v1/{companyId}/machine/{machineId}/firmware/response` | Response to firmware check with version and download URL |

## 4. Detailed Usage Guide

### 4.1 First Boot / Enrollment

A brand-new device has no `machineId`. Use the literal `new` segment in the enroll topic:

**Step 1 — Subscribe to the response topic first:**
```
fp/v1/{companyId}/machine/new/enrolled
```

**Step 2 — Publish the enroll message:**
```
Topic: fp/v1/{companyId}/machine/new/enroll
QoS: 1
```
```json
{
  "pin_no": 99,
  "unit_name": "Biglia_2.0_test",
  "wifi_id": "Factory_SSID",
  "bluetooth_id": "*",
  "ts": 1747564427000
}
```

**Step 3 — Receive the assigned `machineId`:**
```json
{
  "machine_id": 47,
  "status": "created",
  "ts": 1747564427500
}
```

**Step 4 — Store `machineId` persistently** (config file, flash memory, etc.).

From this point on, use `machineId = 47` in all subsequent topics. On the next boot, publish a heartbeat to `fp/v1/{companyId}/machine/47/heartbeat`.

**Python example (paho-mqtt):**
```python
import paho.mqtt.client as mqtt
import json, time

COMPANY_ID = 5
BROKER = "mqtts://mqtt.fpanalyzer.com"

assigned_machine_id = None

def on_connect(client, userdata, flags, rc):
    client.subscribe(f"fp/v1/{COMPANY_ID}/machine/new/enrolled", qos=1)
    client.publish(
        f"fp/v1/{COMPANY_ID}/machine/new/enroll",
        json.dumps({
            "pin_no": 99,
            "unit_name": "Biglia_2.0_test",
            "wifi_id": "Factory_SSID",
            "bluetooth_id": "*",
            "ts": int(time.time() * 1000)
        }),
        qos=1
    )

def on_message(client, userdata, msg):
    global assigned_machine_id
    payload = json.loads(msg.payload)
    assigned_machine_id = payload["machine_id"]
    save_to_config(assigned_machine_id)  # persist to flash/file

client = mqtt.Client(client_id="machine-5-0", clean_session=False)
client.username_pw_set("machine-5-0", "your-provisioned-password")
client.on_connect = on_connect
client.on_message = on_message
client.connect(BROKER, 8883)
client.loop_forever()
```

### 4.2 Heartbeat

Publish to the `heartbeat` topic every 30–60 seconds (or immediately on power-up). The server updates `last_online` and emits a `machine:status:changed` WebSocket event to the dashboard. If `firmware_version` is behind the server's configured latest version, the server also emits a `machine:firmware:update:available` event.

No response topic — heartbeat is a one-way signal.

```python
import time, json

def send_heartbeat(client, company_id, machine_id):
    client.publish(
        f"fp/v1/{company_id}/machine/{machine_id}/heartbeat",
        json.dumps({
            "machine_id": machine_id,
            "pin_no": 1,
            "unit_name": "Montering Input - 1",
            "wifi_id": "Factory_SSID",
            "bluetooth_id": "*",
            "firmware_version": "1.3.0",
            "ts": int(time.time() * 1000)
        }),
        qos=1,
        retain=True
    )
```

**Heartbeat retain flag:** The `heartbeat` topic uses `retain=True`. This means the broker stores the last heartbeat so that the Express backend immediately knows each machine's state when it (re)connects — no polling required.

### 4.3 Stop Detection

When the machine stops, publish to `stop/start` immediately with the current time as `start_time`. The server opens a `machine_data` row with `end_time = NULL` and emits a `machine:stop:started` WebSocket event.

```python
import datetime, time, json

def on_machine_stop(client, company_id, machine_id):
    start_time = datetime.datetime.utcnow().strftime("%Y-%m-%dT%H:%M:%SZ")
    # Save start_time locally — you will need it in stop/end
    save_stop_start_time(start_time)

    client.publish(
        f"fp/v1/{company_id}/machine/{machine_id}/stop/start",
        json.dumps({
            "machine_id": machine_id,
            "start_time": start_time,
            "ts": int(time.time() * 1000)
        }),
        qos=1
    )
```

**Deduplication:** QoS 1 guarantees at-least-once delivery. If the device re-publishes a `stop/start` message that was already processed (e.g., after a broker restart), the server uses the MQTT packet ID to detect and skip the duplicate. No additional field is required in the payload.

**Long-stop suppression:** If the machine is already in a stopped state (open `machine_data` row exists), the server silently ignores a second `stop/start`. It does not create a duplicate row.

### 4.4 Machine Restart / Stop End

When the machine restarts, publish to `stop/end` with both `start_time` (from when the stop was detected) and `end_time` (now). The server looks up the `machine_data` row whose `start_time` matches exactly and sets its `end_time`.

```python
import datetime, time, json

def on_machine_restart(client, company_id, machine_id):
    start_time = load_stop_start_time()  # retrieved from local storage
    end_time = datetime.datetime.utcnow().strftime("%Y-%m-%dT%H:%M:%SZ")

    client.publish(
        f"fp/v1/{company_id}/machine/{machine_id}/stop/end",
        json.dumps({
            "machine_id": machine_id,
            "start_time": start_time,
            "end_time": end_time,
            "ts": int(time.time() * 1000)
        }),
        qos=1
    )
```

**Critical:** The `start_time` in `stop/end` must exactly match the `start_time` sent in the earlier `stop/start`. The server uses this to find the correct open row. If no exact match is found, it falls back to closing the most recent open row and logs a warning.

**This is an improvement over the HTTP API:** The old `installV1` endpoint always closed the most recent open row, which caused data corruption if two stops occurred before a restart. MQTT fixes this by using `start_time` as the lookup key.

### 4.5 Offline Buffer / Replay

If the device cannot reach the broker (factory network outage), buffer stop events locally. When the connection resumes, publish all buffered events as a single `stop/replay` message.

**Local buffering strategy:**
- Write each stop event (both `start_time` and `end_time`) to local SQLite or a file queue.
- Include a flag for whether the data is valid (`is_valid_data`).

**On reconnect:**
```python
import json, time

def flush_offline_buffer(client, company_id, machine_id, buffered_events):
    # buffered_events: list of {"start_time":..., "end_time":..., "is_valid_data":True}
    client.subscribe(
        f"fp/v1/{company_id}/machine/{machine_id}/stop/replay/ack", qos=1
    )
    client.publish(
        f"fp/v1/{company_id}/machine/{machine_id}/stop/replay",
        json.dumps({
            "machine_id": machine_id,
            "events": sorted(buffered_events, key=lambda e: e["start_time"]),
            "ts": int(time.time() * 1000)
        }),
        qos=1
    )

def on_replay_ack(client, userdata, msg):
    ack = json.loads(msg.payload)
    if ack["failed_at"] is not None:
        # Remove committed events from buffer; retry from failed_at
        retry_from = ack["failed_at"]
        # ... re-publish remaining events
    else:
        # All events committed — clear the local buffer
        clear_offline_buffer()
```

**ACK response from server:**
```json
{
  "committed": 2,
  "total": 3,
  "failed_at": 2,
  "ts": 1747565100500
}
```

If `failed_at` is not null, it is the zero-based index of the first event that failed. Retry from that index.

**Events must be sorted by `start_time` ascending** — the server sorts them before processing, but sending them in order reduces the chance of auto-registration cascade issues.

**QoS 1 vs replay topic:** If the device can reach the broker but Express is temporarily down, QoS 1 with persistent sessions handles delivery automatically — the broker queues the messages and delivers them when Express reconnects. The `stop/replay` topic is only needed for when the broker itself was unreachable.

### 4.6 Firmware Version Check

Two options:

**Option A (recommended for simplicity): keep using HTTP**
```
POST /api/v1/machine/checkIotLatestVersion
Body: {"version": "1.3.0"}
```
The HTTP endpoint continues to work. Use it if the device already has a JWT or legacy email auth.

**Option B: MQTT request-response**
```python
def check_firmware(client, company_id, machine_id, current_version):
    client.subscribe(
        f"fp/v1/{company_id}/machine/{machine_id}/firmware/response", qos=0
    )
    client.publish(
        f"fp/v1/{company_id}/machine/{machine_id}/firmware/check",
        json.dumps({
            "machine_id": machine_id,
            "current_version": current_version,
            "ts": int(time.time() * 1000)
        }),
        qos=0
    )
```

Server response on `firmware/response`:
```json
{
  "current_version": "1.2.7",
  "latest_version": "1.3.0",
  "upgrade_available": true,
  "download_url": "/iot_version/software/latest.bin",
  "ts": 1747565100200
}
```

The MQTT firmware check uses proper semver comparison (per-component), unlike the HTTP endpoint which had a known version-comparison bug.

### 4.7 Status and Last Will and Testament

**On CONNECT:** Set the LWT (see section 2.5) so the broker auto-publishes offline status on abnormal disconnect.

**On successful connection:** Publish the online status to overwrite any retained LWT message:
```python
def on_connect(client, userdata, flags, rc):
    client.publish(
        f"fp/v1/{COMPANY_ID}/machine/{MACHINE_ID}/status",
        json.dumps({
            "machine_id": MACHINE_ID,
            "connected": True,
            "reason": "connect",
            "ts": int(time.time() * 1000)
        }),
        qos=1,
        retain=True
    )
```

**On graceful shutdown:** Publish offline status before disconnecting:
```python
def on_shutdown(client, company_id, machine_id):
    client.publish(
        f"fp/v1/{company_id}/machine/{machine_id}/status",
        json.dumps({
            "machine_id": machine_id,
            "connected": False,
            "reason": "graceful",
            "ts": int(time.time() * 1000)
        }),
        qos=1,
        retain=True
    )
    client.disconnect()
```

The server handles all three status payloads (lwt, connect, graceful) by updating `machines.unit_connected` and emitting `machine:online` or `machine:offline` WebSocket events.

## 6. Error Handling and Retries

### 6.1 QoS 1 and Deduplication

Stop events (`stop/start`) use QoS 1 (at-least-once delivery). The broker guarantees the message reaches Express at least once. If the `PUBACK` is lost, the broker re-delivers with the DUP flag set.

The server deduplicates using the MQTT packet ID: before inserting a `machine_data` row, it checks whether a row with that packet ID already exists. If so, the duplicate is silently discarded. No application-level deduplication field is required in the payload.

### 6.2 Offline Buffering

When the broker is unreachable:

1. Write each stop event to local persistent storage (SQLite, file queue).
2. Continue normal operation; the device marks the machine state locally.
3. On broker reconnect, publish the buffered events via `stop/replay`.
4. Wait for `stop/replay/ack` and remove acknowledged events from the buffer.

### 6.3 Reconnect Strategy

Use exponential backoff with jitter:

```python
import time, random

BASE_DELAY = 1     # seconds
MAX_DELAY  = 60    # seconds

delay = BASE_DELAY
while not connected:
    time.sleep(delay + random.uniform(0, delay * 0.1))
    try_connect()
    delay = min(delay * 2, MAX_DELAY)
```

Paho-mqtt handles reconnection automatically if `reconnect_on_failure=True` (default). For fine-grained control, implement the backoff in the `on_disconnect` callback.

### 6.4 Timestamp Staleness Rejection

The server rejects messages where `|serverTime - ts| > 60,000 ms`. Ensure the device's system clock is synchronized (NTP). If the device clock is known to drift, synchronize it immediately after network connection is established.

**Special case:** The LWT payload must use `ts: 0` (not a real timestamp), because the LWT is set at connect time but may be fired by the broker hours later.

### 6.5 Stale `start_time` in stop/end

If a device reboots unexpectedly between `stop/start` and `stop/end`, it may lose the `start_time` from local memory. In this case, publish `stop/end` without a `start_time` — the server will close the most recent open row as a fallback and log a warning. This is a graceful degradation, not a fatal error.

## 8. Migration Checklist for Existing HTTP Devices

Follow these steps to migrate a device from the legacy HTTP API to MQTT.

### Pre-migration

- [ ] **Provision MQTT credentials** via `POST /api/v1/admin/iot/units/{machineId}/provision-mqtt` (admin JWT required).
- [ ] **Store credentials securely** on the device (username, password, broker URL). The password is shown once only.
- [ ] **Obtain TLS CA certificate** for the production broker.

### Firmware Changes

- [ ] **Add MQTT client library** (`paho-mqtt` for Python, `mqtt` npm package for Node.js).
- [ ] **Implement MQTT connection** with:
  - `clean_session = false`
  - Stable client ID (`machine-{companyId}-{machineId}`)
  - TLS on port 8883 (production)
- [ ] **Set LWT on CONNECT** to `fp/v1/{companyId}/machine/{machineId}/status` with `{"connected":false,"reason":"lwt","ts":0}`.
- [ ] **Publish online status** on connect to the `status` topic with `connected: true`.
- [ ] **Replace heartbeat:** Remove `installV1` heartbeat calls. Publish to `fp/v1/{companyId}/machine/{machineId}/heartbeat` every 30–60 seconds.
- [ ] **Replace stop detection:** Remove `saveStopDataV1` calls. Publish to `fp/v1/{companyId}/machine/{machineId}/stop/start`. Save `start_time` locally.
- [ ] **Replace restart/stop-end:** Remove `installV1` restart calls. Publish to `fp/v1/{companyId}/machine/{machineId}/stop/end` with both `start_time` (saved locally) and `end_time`.
- [ ] **Implement local buffering:** Write stop events to SQLite/file queue when broker is unreachable.
- [ ] **Implement replay:** Publish `stop/replay` on reconnect with buffered events. Listen for `stop/replay/ack`.
- [ ] **Publish graceful offline status** before device shutdown.

### Testing

- [ ] Test heartbeat → verify dashboard shows device online.
- [ ] Test stop/start → verify dashboard shows machine stopped.
- [ ] Test stop/end → verify dashboard shows machine running, stop duration is correct.
- [ ] Test offline buffering → disconnect broker, create stops, reconnect, verify replay/ack.
- [ ] Test LWT → kill the MQTT connection (power pull); verify dashboard shows offline within 90 seconds.
- [ ] Test enrollment (if applicable for new units).

### Cutover

- [ ] **Remove HTTP calls** (optional — HTTP endpoints remain active during migration period).
- [ ] Confirm `mqtt_provisioned_at` is populated in the `machines` table for this device.

## 9. Common Pitfalls and Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| Heartbeat has no effect on dashboard | Missing `pin_no` or `unit_name` in payload | Both fields are required for `installMachine` to process the heartbeat |
| Stop is never closed (no `end_time`) | `start_time` in `stop/end` doesn't match `start_time` from `stop/start` | Store `start_time` in persistent local storage; use exact same string |
| Duplicate stop rows in database | Sending `stop/start` more than once for the same stop event | The server deduplicates using the MQTT packet ID; verify you're not reconnecting with a new client ID between sends (which resets packet IDs) |
| Replay events not processed | Events in `events[]` are not chronologically sorted | Sort by `start_time` ascending before publishing |
| Server rejects all messages with `ts` error | Device clock is drifted > 60 seconds | Sync NTP immediately on boot. Check logs for `[MQTT] stale message rejected` |
| LWT not firing | `clean_session = true` or LWT not set on CONNECT | Set `clean_session = false` and configure LWT before calling `connect()` |
| Dashboard shows machine online after power failure | LWT retained message was overwritten by a stale online message | Always publish `connected: true` to status right after connect so the retained value is current |
| Connection refused at broker | Using wrong client ID (must match provisioned username) | Client ID must be `machine-{companyId}-{machineId}` exactly |
| `enrolled` response never received | Not subscribed before publishing `enroll` | Subscribe to `fp/v1/{companyId}/machine/new/enrolled` before publishing `enroll` |
| WebSocket dashboard not updating | `companyId` in topic doesn't match the tenant schema | Verify the company integer ID used in the topic matches the provisioned credentials |
| Firmware update badge not appearing | `firmware_version` missing from heartbeat | Include `firmware_version` in every heartbeat; server compares it passively |

### Parsing the Response

```python
import json

response = json.loads(api_response_body)
data = response["data"]

MACHINE_ID  = data["machineId"]     # 9
USERNAME    = data["username"]       # "machine-5-9"
CLIENT_ID   = data["clientId"]       # "machine-5-9" (same as username)
PASSWORD    = data["password"]       # plaintext — store securely
BROKER_URL  = data["brokerUrl"]      # "mqtts://mqtt.fpanalyzer.com:8883"
ACL_PREFIX  = data["aclTopicPrefix"] # "fp/v1/5/machine/9/#"

# Parse broker URL
from urllib.parse import urlparse
parsed = urlparse(BROKER_URL)
BROKER_HOST = parsed.hostname   # "mqtt.fpanalyzer.com"
BROKER_PORT = parsed.port       # 8883
USE_TLS     = parsed.scheme == "mqtts"

# Extract companyId from the ACL topic prefix
COMPANY_ID = int(ACL_PREFIX.split("/")[2])  # 5
```

### Saving Credentials to Config File

```python
import json, os

config = {
    "machine_id": MACHINE_ID,
    "company_id": COMPANY_ID,
    "mqtt_username": USERNAME,
    "mqtt_password": PASSWORD,  # store securely; consider encrypting at rest
    "mqtt_broker": BROKER_HOST,
    "mqtt_port": BROKER_PORT,
    "mqtt_tls": USE_TLS
}

with open("/etc/fpanalyzer/device.json", "w") as f:
    json.dump(config, f, indent=2)

os.chmod("/etc/fpanalyzer/device.json", 0o600)  # owner-read only
```

### ACL Enforcement

The broker enforces ACL rules per device. The provisioned device (`machine-5-9`) can only:
- Publish to `fp/v1/5/machine/9/#`
- Subscribe to `fp/v1/5/machine/9/#`

It cannot publish to any other machine's topics or any other company's topics. This is enforced at the broker level, independent of the Express backend.

The Express backend uses a superuser account (`express-backend`) that has read/write access to all topics under `fp/#`.
