1 — What the server does

The server records machine downtime. A machine stops, the Pi reports it, a stop record opens. The machine restarts, the Pi reports that, the record closes and the duration becomes downtime in the OEE reports. Everything else in this document exists to make that one thing reliable when the network is not. 

  Factory floor                          Cloud
  ┌──────────────────────┐
  │ GPIO producer   ─┐   │   TLS 8883    ┌────────────┐    ┌──────────────────┐
  │ local queue     ─┼───┼──────────────▶│ Mosquitto  │───▶│ Express backend  │──▶ Postgres
  │ MQTT 5 client  ◀─┘   │  (QoS 1,      │  broker    │◀───│ (idempotent)     │──▶ dashboard
  │  (own thread)        │  persistent)  └────────────┘    └──────────────────┘     (WebSocket)
  └──────────────────────┘
        one per Pi                  auth against public.mqtt_devices
One credential per Pi, not per machine A Pi carries up to four machines on pins 1–4. It opens one MQTT connection with one username, and pin_no inside the payload says which machine an event belongs to. This is the biggest structural change from the old HTTP firmware.

2 — What changed from your design

Most of your architecture document was adopted as written: the unified ON/OFF event, client-generated event_id for idempotency, LWT presence, the durable local queue, hybrid OTA, and the three-thread fault-isolation model. Four things differ.

Your designWhat the server implementsWhy
fp/{company-slug}/{unit}/… fp/{companyId}/{unit}/… — an integer That integer is the tenant id; it selects the Postgres schema directly. A slug would need a lookup table that buys nothing.
Per-device X.509 (mTLS) Username + password over TLS Credentials live in Postgres and are individually revocable, which was the actual requirement. Topics and ACLs do not change if we move to mTLS later.
First-boot enrollment over MQTT Provisioned out of band A factory-fresh unit has no broker credentials, so it cannot connect at all. Everything after provisioning is MQTT.
req/login returns an auth result Stub that always succeeds Reaching the topic already required valid broker credentials — the connection is the authentication.

3 — Connection parameters

Your ACL confines you to your own subtree You may publish and subscribe only under fp/{companyId}/{unitName}/#. We tested this: a valid unit publishing into another company's subtree is dropped by the broker and never reaches the backend. The server also refuses to reply to a Response Topic outside your subtree.

4 — Getting credentials

An administrator provisions each physical unit, either in the admin UI (IoT → IoT units → Add unit) or on the server:

# issues credentials for one Raspberry Pi
node backend/scripts/provision-mqtt-unit.js 11 UNIT-01

You receive three things per Pi:

ItemExampleWhere it goes
username / client idfp-11-UNIT-01MQTT CONNECT
passwordkJ8x2mQ… (32 chars)MQTT CONNECT — shown once, not recoverable
CA certificateca.crt/etc/fpanalyzer/ca.crt

Revocation takes effect within about 60 seconds (the broker caches auth results for that long). Re-provisioning a unit issues a new password that must be entered on the device.

5 — The lifecycle, step by step

Once, before the Pi ships

An administrator provisions the unit and you write the username, password and ca.crt onto the device. Nothing is needed from the firmware at this stage.

Every boot

  1. Sync the clock. NTP, before the first publish. See §12 — this matters more than it looks.
  2. Register the Last Will before calling connect: 
    topic   fp/{companyId}/{unit}/status/conn      retain=true  qos=1
payload {"online": false, "reason": "lwt"}
  3. Connect over TLS 8883, clean_start=false, client id = username.
  4. Publish presence, retained, which overwrites the stored Last Will: 
    fp/{companyId}/{unit}/status/conn
{"online": true, "reason": "connect", "fw": "2.1.7", "ip": "192.168.1.7"}
  5. Subscribe to fp/{companyId}/{unit}/resp/# and fp/{companyId}/{unit}/cmd/#.
  6. Publish a retained pin snapshot to status/machines.
  7. Optional: ask req/version whether an update applies.

While running

  GPIO transition
     │
     ├─▶ stamp UTC time + generate a UUIDv4  ← at CAPTURE, never at send time
     ├─▶ write the event to the local SQLite queue
     ├─▶ MQTT thread publishes fp/{c}/{u}/evt/machine  qos=1
     └─▶ delete the queue row ONLY after PUBACK

When the network drops

Keep capturing. Keep queuing. Machine monitoring must never stop because the network did. On reconnect, drain the queue oldest-first with buffered: true and the original ts and event_id.

Reconnect with randomized exponential backoff — base 1 s, ×2, cap 60 s, ±20 % jitter. With hundreds of units this is not optional; without it the broker gets hammered exactly when it is weakest.

On power loss

Nothing to do. The broker publishes your Last Will automatically after roughly 1.5× keepalive (~90 s), and the dashboard shows the unit offline.

6 — Topic reference

All topics are fp/{companyId}/{unitName}/{class}/{name}. companyId is an integer we give you; unitName is the unit's name, 1–50 characters of A–Z a–z 0–9 . _ -, stable for the life of the device.

Device → server

TopicDirQoSRetainPurpose
…/evt/machine▲ UP1noMachine ON/OFF transition — the only event carrying data
…/evt/ota▲ UP1noFirmware update progress
…/status/conn▲ UP1yesPresence; also the Last Will
…/status/machines▲ UP1yesSnapshot of all four pins
…/req/register▲ UP1noGet the machine id for a pin
…/req/version▲ UP1noAsk whether an update applies
…/req/login▲ UP1noCompatibility stub, always succeeds

Server → device — subscribe to these

TopicDirQoSRetainPurpose
…/resp/{op}▼ DOWN1noReply to req/{op}
…/cmd/config▼ DOWN1yesPin enable flags + debounce windows
…/cmd/ota▼ DOWN1noFirmware URL + SHA-256
…/cmd/reboot▼ DOWN1noDelayed restart
Anything else is ignored The backend consumes only the topics above. Publishing to another topic under your own subtree is accepted by the broker and silently dropped by the server — no error will come back.

7 — evt/machine — the only data event

fp/11/UNIT-01/evt/machine        qos 1, retain false
{
  "event_id": "9f2c1b7a-4c31-4a6e-9c21-1d5f0b7a2e11",
  "seq":      10432,
  "pin_no":   1,
  "state":    "OFF",
  "ts":       "2026-08-21T10:00:00.000Z",
  "buffered": false,
  "fw":       "2.1.7"
}
FieldRequiredRules
event_idyes UUIDv4, lowercase. Generated once at capture and reused on every retry and replay. This is the deduplication key — the single most important field in this document.
seqrecommended Monotonic per unit, persisted across reboots. Gaps are detected and surfaced on the dashboard as lost events.
pin_noyes Integer 1–4. Anything else is rejected outright.
stateyes "ON" or "OFF", case-insensitive. OFF = machine stopped. ON = machine restarted.
tsyes ISO-8601 UTC with milliseconds and a Z suffix. Stamped at GPIO capture, never at send time. Rejected if before 2020 or more than 24 h in the future.
bufferedoptional true when replayed from the local queue. Defaults to false.
fwoptional Firmware version string; also updates the unit's reported version.

What the server does with it

  • state: "OFF" → opens a stop record with start_time = ts.
  • state: "ON" → closes the most recent open stop record with end_time = ts and computes the duration.
  • A unit+pin the server has never seen is created automatically as an unconfigured machine and appears in the admin list awaiting assignment. No registration call is needed.
The ON event does not need to know when the stop began There is no timestamp matching anywhere. The old firmware had to repeat the exact start_time string on the restart message, and if it did not match byte-for-byte the wrong record was closed. That whole class of bug is gone.

8 — status/conn and status/machines

status/conn — presence

Publish retained, QoS 1, immediately after connecting. On a clean shutdown publish {"online": false, "reason": "shutdown"} then disconnect cleanly.

{"online": true, "reason": "connect", "fw": "2.1.7", "ip": "192.168.1.7"}

This replaces the old 180-second HTTP heartbeat entirely. Do not poll.

status/machines — snapshot

Publish retained, QoS 1, after connect and whenever pin configuration changes.

{
  "fw": "2.1.7",
  "dropped_count": 0,
  "machines": [
    {"pin_no": 1, "state": "ON",  "enabled": true},
    {"pin_no": 2, "state": "OFF", "enabled": true},
    {"pin_no": 3, "state": "OFF", "enabled": false},
    {"pin_no": 4, "state": "ON",  "enabled": true}
  ]
}

dropped_count is your local buffer overflow counter. Report it; never drop events silently. The dashboard shows it as a warning against the unit.

Drift is logged, not reconciled If your reported state disagrees with the database, the server logs it and flags the unit but does not correct the records — inventing transitions that never happened would corrupt downtime reporting. Drift means events were lost; it should be investigated, not papered over.

9 — req/resp — asking the server

Publish to req/{op}. On MQTT 5 set Response Topic (must be inside your own subtree) and Correlation Data; the server echoes both. On 3.1.1 omit them — the reply lands on resp/{op} and req_id is echoed in the body.

Timeout 10 s, retry 3× with backoff. If no reply arrives, carry on with last-known values and retry later. Never block machine capture on a reply.

req/register — get the machine id for a pin

→ {"req_id": "c7a1…", "pin_no": 1, "fw": "2.1.7", "ip": "192.168.1.7"}
← {"req_id": "c7a1…", "success": true, "pin_no": 1, "machine_id": 125, "configured": true}

Idempotent — asking twice returns the same id. configured: false means no operator has bound the machine to equipment yet; keep reporting events anyway, they are stored and become valid once binding happens.

You do not strictly need this call — evt/machine resolves the machine from (unit, pin_no) on its own. Use it if you want the id for local display.

req/version — should I update?

→ {"req_id": "d1b2…", "fw": "2.1.7"}
← {"req_id": "d1b2…", "success": true, "update_available": true,
   "version": "2.1.8", "url": "https://…/fp_2.1.8.zip",
   "sha256": "e3b0c442…", "size": 10485760, "notes": "…", "mandatory": false}
Do no version arithmetic on the device The server decides. Act on update_available alone. The old firmware compared version strings, which is why every x.y.10 release was missed — "2.1.10" < "2.1.9" as text.

10 — cmd/* — commands from the server

Subscribe to fp/{companyId}/{unit}/cmd/# after connecting.

Hard rule: the MQTT thread never touches GPIO Validate the command, hand it to the control thread through a queue, and let that thread apply it. A malformed or hostile command must not be able to drive a relay from the network path. This is your own §12 — we are holding you to it.

cmd/config — retained

{"cmd_id": "…", "off_on_ms": 100, "on_off_ms": 100,
 "pins": {"1": true, "2": true, "3": false, "4": true}}

Retained, so a rebooting unit receives current settings on subscribe without asking. Only keys present are being changed. Pin keys outside 1–4 are stripped server-side.

cmd/reboot

{"cmd_id": "…", "delay_s": 5}

11 — Firmware updates

The URL rides MQTT; the bytes ride HTTPS. The binary is never chunked over the broker.

fp/11/UNIT-01/cmd/ota
{"cmd_id": "…", "version": "2.1.8",
 "url": "https://dev.fpanalyzer.se/downloads/fp_2.1.8.zip",
 "sha256": "e3b0c442…", "size": 10485760, "force": false}

Required device behaviour, in order:

  1. Download over HTTPS, streaming, treating size as an upper bound.
  2. Compute SHA-256 and abort unless it matches.
  3. Extract to a staging directory, swap a current symlink, then reboot. Never extract in place — a half-download must not brick the unit.
  4. Report each step on evt/ota.

evt/ota — progress

{"cmd_id": "…", "state": "verifying", "version": "2.1.8", "detail": "sha256 ok"}

state is one of downloading, verifying, applying, success, failed. Anything else is ignored. On failure put the reason in detail — it is shown in the admin fleet view.

The hash check is mandatory The install path runs as root. The server refuses to publish a release without a SHA-256, and the device must refuse to install one. This closes the unverified-package finding in your own API audit.

12 — Five rules that cause most bugs

  1. event_id must survive a reboot. Write the event to the queue with its UUID before publishing, and delete the row only after PUBACK. A fresh UUID on retry creates a duplicate record; the same one is absorbed silently. This is the entire deduplication mechanism.
  2. UTC only, with milliseconds and a Z. The old firmware sent local time on one code path and UTC on another, with no timezone marker. Everything is UTC now.
  3. Sync NTP at boot. ts is capture time and the server does not reject old timestamps — buffered replay depends on that. But a clock that is wrong by hours produces wrong reports with no error anywhere. This is the failure mode most likely to waste a day.
  4. Client ID must equal the username. Not similar — identical. A mismatch is refused at CONNECT.
  5. Persist seq across reboots. Otherwise every restart looks like a gap and the dashboard reports lost events that were never lost.

13 — Reference implementation

Skeleton only — the queue and GPIO layers are yours.

import json, time, uuid
import paho.mqtt.client as mqtt

COMPANY_ID, UNIT = 11, "UNIT-01"
USER = f"fp-{COMPANY_ID}-{UNIT}"
BASE = f"fp/{COMPANY_ID}/{UNIT}"
FW   = "2.1.7"

c = mqtt.Client(client_id=USER, clean_session=False, protocol=mqtt.MQTTv5)
c.username_pw_set(USER, PASSWORD)
c.tls_set(ca_certs="/etc/fpanalyzer/ca.crt")

# Last Will registered BEFORE connect. ts is omitted deliberately: the broker
# fires this minutes later, so any timestamp we wrote here would be wrong.
c.will_set(f"{BASE}/status/conn",
           json.dumps({"online": False, "reason": "lwt"}),
           qos=1, retain=True)

c.connect("dev.fpanalyzer.se", 8883, keepalive=60)
c.loop_start()
c.subscribe([(f"{BASE}/resp/#", 1), (f"{BASE}/cmd/#", 1)])
c.publish(f"{BASE}/status/conn",
          json.dumps({"online": True, "reason": "connect", "fw": FW}),
          qos=1, retain=True)

def utc_now():
    return time.strftime("%Y-%m-%dT%H:%M:%S.000Z", time.gmtime())

def on_gpio_change(pin_no, is_running):
    # Identity and time are stamped HERE, at capture — never at send time.
    event = {
        "event_id": str(uuid.uuid4()),
        "seq":      next_seq(),        # monotonic, persisted to disk
        "pin_no":   pin_no,
        "state":    "ON" if is_running else "OFF",
        "ts":       utc_now(),
        "buffered": False,
        "fw":       FW,
    }
    queue_insert(event)                     # persist BEFORE publishing

def drain_queue():
    for row in queue_oldest_first():
        info = c.publish(f"{BASE}/evt/machine", json.dumps(row), qos=1)
        info.wait_for_publish()
        queue_delete(row["event_id"])      # only after PUBACK

14 — Testing without firmware

You can exercise the whole server path from a laptop with mosquitto_pub before any firmware exists.

# replace COMPANY_ID, UNIT and PASSWORD with your provisioned values
export C=11 U=UNIT-01 PW='your-password'
export OPTS="-h dev.fpanalyzer.se -p 8883 --cafile /etc/fpanalyzer/ca.crt -u fp-$C-$U -P $PW"

# 1. come online (retained)
mosquitto_pub $OPTS -t "fp/$C/$U/status/conn" -q 1 -r \
  -m '{"online":true,"reason":"connect","fw":"2.1.7"}'

# 2. machine on pin 1 stops
mosquitto_pub $OPTS -t "fp/$C/$U/evt/machine" -q 1 \
  -m "{\"event_id\":\"$(uuidgen | tr 'A-Z' 'a-z')\",\"seq\":1,\"pin_no\":1,\
\"state\":\"OFF\",\"ts\":\"$(date -u +%Y-%m-%dT%H:%M:%S.000Z)\",\"buffered\":false}"

# 3. machine restarts — note the NEW event_id
mosquitto_pub $OPTS -t "fp/$C/$U/evt/machine" -q 1 \
  -m "{\"event_id\":\"$(uuidgen | tr 'A-Z' 'a-z')\",\"seq\":2,\"pin_no\":1,\
\"state\":\"ON\",\"ts\":\"$(date -u +%Y-%m-%dT%H:%M:%S.000Z)\",\"buffered\":false}"

Then open IoT → IoT units in the admin UI. The unit should show Online, and a stop record with its duration should appear without refreshing the page.

Connection refused: not authorisedClient ID is not exactly the username, wrong password, or the unit was revoked

16 — What we need from you

  1. Confirm you will build to this document, not to the architecture HTML — particularly the integer {companyId} topic segment.
  2. Your unit naming scheme. unitName becomes an MQTT topic segment: 1–50 characters of A–Z a–z 0–9 . _ -, stable for the life of the device.
  3. Confirm pins per unit. We assume up to four (GPIO 17, 27, 22, 5 → pins 1–4). The server rejects anything outside 1–4.
  4. Fix the v1 client bugs you documented, since those devices are still in the field: the fetchone() batch loop that uploads four of every five records but deletes all five; stops not being buffered offline; the hard-coded test.fpanalyzer.se in four files; the plaintext password in settings.ini.
  5. Tell us whether you want mTLS in a later phase. The design is ready for it — a broker config change plus a certificate pipeline, no protocol change.

Open on our side, in the interest of honesty

  • Broker high availability. Still a single Mosquitto node. Your §2 is right that this is the real risk at fleet scale, not throughput. Not yet resolved.
  • Package signing. We enforce SHA-256, which proves the file is intact but not who made it. As your document notes, whoever controls the version response controls the hash. Signing is the proper fix and is not built.
