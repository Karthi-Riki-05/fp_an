FP Analyzer — Machine API Reference

HTTP endpoints the FP Analyzer Raspberry Pi client currently calls. Reverse-engineered from client source v2.1.7 (main.py, machineStart.py, machineStop.py, fpmain.py). Server-side behaviour is inferred from how the client sends and reads each call.
Base: https://test.fpanalyzer.se/api/machine/ Client v2.1.7 7 endpoints
Environment note: every call points at the test host test.fpanalyzer.se. There is no production base URL anywhere in the source — the same string is hard-coded in four files. Swapping environments today means editing code, not config.

Overview & conventions

Base URL
https://test.fpanalyzer.se/api/machine/
Transport
All writes are POST with an application/x-www-form-urlencoded body (Python requests(data=…)). The package download is a streamed GET.
Response format
JSON. Most endpoints return { "success": bool, "data": {…} }. A call is treated as OK only when HTTP status is 200 and success is true.
Timestamps
main.py sends local time as YYYY-MM-DD HH:MM:SS.ffffff. fpmain.py sends datetime.utcnow(). Timezone is not carried in either.
⚠ Inconsistent timestamp basis Two client paths report time in two different bases (local vs UTC) with no timezone marker. If both paths ever hit the same account, server-side reports will be skewed by the Pi's local offset.

The standard success envelope, as the client expects it:

// generic success
{ "success": true, "data": { /* endpoint-specific */ } }

// generic failure (client falls back to local buffering or an error label)
{ "success": false }

Authentication model

There is no token or session. The flow is:

1. The device calls /login once with an email + password. The response is only a boolean — no token, cookie, or key is issued.
2. Every subsequent call re-identifies the caller by resending company_email_id (the login email), and for device-scoped calls also unit_name.
3. Credentials are cached on the device in settings.ini and replayed automatically on reconnect.

✖ Security: credentials at rest & no revocation The password is stored in settings.ini in plaintext and re-validated on every reconnect. Because identity is just an email string on each request and no token is issued, there is no way to expire or revoke a single device's access without changing the account password everywhere.

Called from

Request body

FieldTypeExampleNotes
email requiredstringtest@fpanalyzer.seThe "User ID" field in the UI — an email address.
password requiredstring••••••Sent in the POST body. Also persisted plaintext locally.

Response

{ "success": true }   // valid  → client stores creds, proceeds to unit setup / home
{ "success": false }  // invalid → UI shows "Invalid Login."
⚠ Only a boolean is returned No token/role/expiry comes back, so the client cannot distinguish "wrong password" from "server error" — any non-success response is shown as "Invalid Login."

2 — Install / machine-start / restart overloaded

POST /api/machine/installV1 Registers a machine and reports a machine-ON (start/restart) event; returns the server-assigned machine id.

Called from

main.py → sendrestartdatatoServer() — start/restart (save_restart_url="installV1")
machineStart.py → sendStartDataToServer() — install/start
machineStop.py → sendStopDataToServer() — stop (see warning)
✖ One endpoint, three payloads, three meanings installV1 receives the install shape, the start/restart shape, and a stop shape. In particular machineStop.py posts stop events to installV1, while main.py posts stop events to saveStopDataV1 (endpoint 3). The server must guess intent from which fields are present. Pick one contract per action.

3 — Machine-stop event

POST /api/machine/saveStopDataV1 Reports a machine-OFF (stop) event — the primary GUI path.

Called from

main.py → sendStopDataToServer() (save_stop_url="saveStopDataV1")

Request body

FieldTypeExampleNotes
start_timestring2026-08-20 15:10:07.882000Field name is misleading: it carries the stop moment's timestamp (the last-signal time), not a start time.
machine_idint/string125Server machine id (from the earlier installV1 response).
company_email_idstringtest@fpanalyzer.seLogin email.

Response

{ "success": true }   // parsed but only used for logging; failures aren't retried here
✖ Stop events are lost when offline On this path, if there is no network the client only writes "offInternetfail" to a local log — it does not buffer the stop to SQLite the way start events are buffered. Any machine-stop during an outage never reaches the server, so run-durations will over-count.

4 — Bulk offline sync

POST /api/machine/saveOfflineData Uploads locally buffered events once connectivity returns, in batches of 5.

Called from

main.py → updatefailureData() (reads the fplostdata SQLite table)

Request body

FieldTypeExampleNotes
company_email_idstringtest@fpanalyzer.seLogin email.
unit_namestringUNIT-01Device unit id.
datastring (JSON)["125::2026-08-20 14:03:22::2026-08-20 14:05:01", …]JSON-encoded array of "machine_id::start_time::end_time" strings (double-colon delimited).

Response

{ "success": true }
// on success the client DELETEs the batch locally and recurses for the next 5
✖ Silent data loss in the batch loop updatefailureData() calls fetchone() (consuming the first row) and then iterates the cursor to build data, so the first record of every 5-row batch is omitted from the upload — but deleteData() deletes all 5. Buffered records are destroyed without being sent.
ℹ Only starts are ever buffered Combined with endpoint 3's behaviour, the offline buffer only ever contains start events, so this sync can never recover a missed stop.

5 — Connection heartbeat

POST /api/machine/updateUnitConnectionStatus Periodic "device is online" ping.

Called from

main.py → updateUnitConnectionStatus() (fired by timerFun every ~180 s)

Request body

FieldTypeExampleNotes
company_email_idstringtest@fpanalyzer.seLogin email.
unit_namestringUNIT-01Device unit id.

Response

// response body is never read — fire-and-forget
⚠ Response ignored The client does not check the status or body, so a rejected or failed heartbeat is invisible on the device. The 180 s timer is driven by a multiprocessing.Process that re-arms itself recursively.

6 — Check for update

POST /api/machine/checkIotLatestVersion Asks the server whether a newer app/firmware package exists.

Called from

main.py → checkSoftwareUpdate() (the "update" button on the home screen)

Request body

FieldTypeExampleNotes
versionstring2.1.7Current client version (version_no).

Response

{
  "success": true,
  "data": {
    "version": "2.1.8",              // latest available
    "url": "/downloads/test_fp_analyzer_v2.1.8.zip",
    "info": "release notes text"
  }
}
✖ Version comparison is broken The client tests data.version >= version_no as a string, so "2.1.10" sorts lower than "2.1.7" and a real update is missed. And because it's >=, an already-current device (equal versions) is still prompted to download. Return an explicit boolean like update_available and compare semver numerically.

7 — Download update package

GET https://test.fpanalyzer.se{data.url} Streams the update ZIP referenced by endpoint 6.

Called from

main.py → downLoadLoader()

Request

PartValueNotes
MethodGET, streamedrequests.get(url, stream=True), chunked with a progress bar.
URLhttps://test.fpanalyzer.se + data.urlHost is hard-coded; path comes from the version-check response.

Response

// binary application/zip stream, saved as:
test_fp_analyzer_v<version>.zip
// then extracted to /home/pi, /etc/profile is rewritten, device reboots
✖ Unverified package → root code execution The ZIP is downloaded and extracted with no checksum or signature check, then the install path rewrites /etc/profile and reboots — all running as root (Exec=sudo …). Anyone able to spoof the response or MITM the download gets persistent root on every device. Sign packages and verify the signature before extracting.
