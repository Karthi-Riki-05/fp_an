FP Analyzer — MQTT Architecture & Migration Design

Design for replacing the FP Analyzer REST API with MQTT across a 500+ unit Raspberry Pi fleet on a self-hosted Mosquitto broker. Covers topic namespace, message contracts, QoS & idempotency, presence, reconnect/offline buffering, per-device auth at scale, hybrid OTA, and the phased cutover.
MQTT 5.0 Mosquitto (self-hosted) 500+ devices Hybrid: MQTT + HTTPS OTA TLS 8883
Read this first. At 500+ devices the hard problems are availability and identity, not throughput — one Mosquitto node handles this fleet's event volume trivially. Two design rules from the house MQTT conventions drive everything below: (1) fault isolation — the MQTT client thread never touches GPIO, never runs machine logic, never mutates state directly; it only drains a local queue. (2) every message flow defines schema, QoS, timeout, retry, degraded-mode, and reconnect behaviour.

1 — Scope & design principles

This design moves the device→cloud reporting path from HTTP request/response to MQTT pub/sub, while keeping HTTPS where it genuinely belongs (large binary transfer). It is a hybrid model, not "everything over MQTT".

ConcernTransportWhy
Machine start/stop events, status, presence, commandsMQTT 5.0, QoS 1Sparse, small, many-to-one, needs offline tolerance + live fan-out.
Login / register / version check (request→reply)MQTT 5.0 request/responseResponse Topic + Correlation Data give a native reply channel.
OTA package (multi-MB ZIP)HTTPS GETMQTT is the wrong transport for large binaries; URL + hash are delivered over MQTT.

Principles

  • Fault isolation. Network faults must never stop machine monitoring. The GPIO/event producer and the MQTT client are separate threads that communicate only through a durable local queue.
  • Idempotency over exactly-once. Every event carries a client-generated event_id; the server deduplicates. This is cheaper and more robust than QoS 2, and it also neutralises offline-replay duplicates (which QoS 2 cannot).
  • Capture-time truth. The event timestamp is stamped the instant the GPIO transition happens and written to the local queue — never derived at send time — so buffered events keep their real time.
  • Visible loss only. If the local buffer ever overflows, a counter is reported in status; nothing is dropped silently (this is a direct fix for the current saveOfflineData bug).

✖ Single Mosquitto = single point of failure for all 500 sites Open-source Mosquitto has no native clustering. Throughput is not the risk (one node serves this fleet easily); a broker crash taking every site dark at once is. Pick an HA path deliberately:
  • Active/passive failover — two nodes behind a keepalived VIP with replicated persistence_location; simplest, but retained/session state must be replicated or rebuilt on failover.
  • Clustering broker — EMQX / VerneMQ / HiveMQ / NanoMQ speak the same MQTT 5 contract in this doc, add real clustering and shared subscriptions. Recommended if "all sites dark" is unacceptable. Your message design does not change if you switch.
⚠ Reconnect storm When the broker restarts, 500 devices try to reconnect at once. Mandatory: randomized exponential backoff on every client (see §10). Without it, the broker is hammered exactly when it is weakest.

4 — Authentication & authorization at scale

✖ You cannot hand-manage 500 credentials in a static password file Per-device identity is mandatory so a compromised or cloned unit can be revoked individually and cannot publish as another unit.

Recommended: per-device X.509 (mTLS)

Each unit gets its own client certificate at provisioning; the broker maps the certificate CN to the MQTT username (use_identity_as_username true). No passwords on the device, per-device revocation via CRL, and identity is cryptographic. This also replaces the current plaintext-password login entirely.

Alternative: username/password via a dynamic auth backend

If certs are operationally heavy, use mosquitto-go-auth (or the built-in dynamic security plugin) backed by Postgres/Redis so credentials and ACLs live in a database, not a flat file. Passwords hashed (PBKDF2/bcrypt), never stored plaintext on device.

Per-device topic ACL (both options)

ActionTopic patternScope
Publishfp/{company}/{unit}/#A device may publish only under its own subtree.
Subscribefp/{company}/{unit}/cmd/#, fp/{company}/{unit}/resp/#A device may receive only its own commands/replies.
Backend (service acct)fp/+/+/evt/#, fp/+/+/status/#, fp/+/+/req/# (sub); fp/+/+/{resp,cmd}/# (pub)Broad, but a distinct high-privilege identity.

ACL variables like %u / %c (username / client-id) let one rule enforce "own subtree only" across all 500 devices without per-device rules.

5 — Topic namespace

Hierarchical, tenant- and unit-scoped: fp/{company}/{unit}/{class}/{name}. company is a stable slug (map the login email → company id; do not put an email in a topic). Direction is device-relative.

TopicDirQoSRetainedPurpose
fp/{c}/{u}/evt/machine▲ UP1noMachine ON/OFF events (start & stop, unified).
fp/{c}/{u}/evt/ota▲ UP1noOTA apply progress/result.
fp/{c}/{u}/status/conn▲ UP1yesOnline/offline presence. LWT writes offline here.
fp/{c}/{u}/status/machines▲ UP1yesRetained snapshot of all 4 pin states + fw.
fp/{c}/{u}/req/{op}▲ UP1noRequest; op ∈ {login, register, version}. Sets Response Topic + Correlation Data.
fp/{c}/{u}/resp/{op}▼ DOWN1noReply to the matching request.
fp/{c}/{u}/cmd/{cmd}▼ DOWN1no*Commands; cmd ∈ {ota, config, pin, reboot}. May retain config so a rejoining device gets current settings.

Backend consumes with wildcards: fp/+/+/evt/#, fp/+/+/status/#, fp/+/+/req/#. With a clustering broker, use a shared subscription ($share/g1/fp/+/+/evt/#) to load-balance events across multiple consumer instances.

6 — Message contracts (JSON)

All payloads are UTF-8 JSON. Timestamps are ISO-8601 UTC with milliseconds (fixes the current local-vs-UTC inconsistency). Every UP event carries event_id (UUIDv4, idempotency key) and seq (monotonic per-device counter for gap detection).

6.1 Machine event evt/machine ▲ UP QoS 1

{
  "event_id": "9f2c1b7a-...",   // client UUID — dedup key
  "seq": 10432,                    // monotonic per device; server detects gaps
  "company": "acme",
  "unit": "UNIT-01",
  "pin_no": 1,                     // 1..4  (GPIO 17,27,22,5 → 1..4)
  "machine_id": 125,               // server id; 0 until registered
  "state": "ON",                 // "ON" | "OFF" — unifies start & stop
  "ts": "2026-08-20T14:03:22.114Z", // capture time, UTC
  "buffered": false,              // true when replayed from offline queue
  "fw": "2.1.7"
}

timeout: n/a (fire+track PUBACK) · retry: redeliver from queue until PUBACK · degraded: keep enqueuing locally · reconnect: replay oldest-first with buffered=true

A retained snapshot means a rejoining dashboard or a failed-over backend sees current state immediately without waiting for the next transition.

6.4 Request / response req/{op} ▲ → resp/{op} ▼ QoS 1

The device publishes to req/{op} with MQTT 5 properties Response Topic = fp/{c}/{u}/resp/{op} and Correlation Data = req_id. The backend replies on that topic echoing the correlation id. The client applies a timeout and ret/degrades if no reply arrives.

// req/register  (replaces installV1's register role → returns machine_id)
→ { "req_id":"c7...", "company":"acme", "unit":"UNIT-01", "pin_no":1, "ts":"..." }
← { "req_id":"c7...", "success":true, "pin_no":1, "machine_id":125 }

// req/version  (replaces checkIotLatestVersion — server decides, no string compare)
→ { "req_id":"d1...", "unit":"UNIT-01", "fw":"2.1.7" }
← { "req_id":"d1...", "update_available":true, "version":"2.1.8",
    "url":"https://.../test_fp_analyzer_v2.1.8.zip",
    "sha256":"e3b0c442...", "size":10485760, "notes":"..." }

// req/login — only if you keep password auth; with mTLS this disappears (cert = identity)
→ { "req_id":"a0...", "unit":"UNIT-01", "company":"acme" }
← { "req_id":"a0...", "success":true, "reason":"ok" }

timeout: 10 s wait for correlated reply · retry: 3× with backoff · degraded: proceed with last-known machine_id from retained snapshot, retry later · reconnect: re-issue on session resume

// cmd/config  (replaces unitsetup.ini remote edit: filter times + pin enable)

8 — QoS & idempotency

  • Events / status / commands / req-resp: QoS 1 (at-least-once). Retained on the two status/* topics and optionally cmd/config.
  • Not QoS 2. At 500-device fan-in the 4-packet QoS 2 handshake is costly, and it still would not stop duplicates from offline replay. App-layer idempotency covers both cases for less.
✔ Idempotent server write — the core of correct sync The backend upserts on a unique key (company, unit, event_id). A duplicate (QoS 1 redelivery or offline replay) hits the constraint and is acknowledged-and-ignored. Combined with the monotonic seq, the server can also detect and alert on gaps (lost events) rather than discovering them in a report months later.

9 — Presence via Last Will & Testament

The 180 s polling heartbeat is deleted. Instead:

  • At CONNECT the client registers an LWT: retained status/conn with online:false.
  • On successful connect the client publishes retained status/conn online:true.
  • On graceful shutdown it publishes online:false then disconnects cleanly.
  • On an ungraceful drop the broker publishes the LWT automatically after ~1.5× keepalive.

The backend simply subscribes to fp/+/+/status/conn; presence is accurate within ~90 s with zero device-initiated polling, across all 500 units.

10 — Reconnect & offline store-and-forward

Local durable queue

Keep the existing SQLite buffer but make it the primary path, not an afterthought: the GPIO producer writes every event (ON and OFF) to the queue at capture time with its event_id, seq, and UTC ts. The MQTT thread reads the queue, publishes QoS 1, and deletes a row only after PUBACK. Nothing is sent that was not first persisted.

✔ This corrects two current bugs at once Stops are now buffered exactly like starts, and there is no batch loop that can drop the first row — rows leave the queue one PUBACK at a time.

Reconnect behaviour

  • Backoff: randomized exponential — base 1 s, ×2, cap 60 s, ±20% jitter — so 500 devices do not reconnect in lockstep after a broker blip.
  • Session resume: clean_start=false + session expiry keeps subscriptions and inflight messages across short drops.
  • Replay: on reconnect, drain the queue oldest-first with buffered=true and the original ts; idempotency absorbs any overlap with what the broker already had inflight.

Degraded mode & overflow

  • Broker unreachable → keep buffering; machine monitoring continues (fault isolation, §12).
  • Queue is bounded (by count and/or age). On overflow, drop oldest and increment dropped_count, reported in the next status/machines — loss is visible, never silent.

11 — Hybrid OTA

  1. Server publishes cmd/ota with version, url, sha256, size.
  2. Device downloads the ZIP over HTTPS (streamed), enforcing size as an upper bound.
  3. Device computes SHA-256 and aborts unless it matches. closes the unverified-package RCE
  4. Apply transactionally: extract to a staging dir, swap a current symlink, then reboot — so a half-download never bricks the unit (unlike the current in-place /etc/profile rewrite).
  5. Report each step on evt/ota: verifying → downloading → applying → success|failed with detail.
⚠ Prefer a signature over a bare hash SHA-256 proves integrity, not authenticity — if an attacker controls the version response they control the hash too. Signing the package with a private key the fleet verifies against a pinned public key is the real fix. At minimum, the resp/version/cmd/ota channel must be TLS + authenticated (it is, over MQTT 8883).

Never chunk the binary over MQTT. Payloads are capped (message_size_limit) and QoS 1 reassembly of a 10 MB file across 500 devices would abuse the broker. The URL rides MQTT; the bytes ride HTTPS.

12 — Client threading model (fault isolation)

Three cooperating threads/processes on the Pi, communicating only through queues. This is the house rule that keeps a network fault from ever stopping machine capture — and keeps the network layer from ever driving hardware.

 ┌───────────────┐  event   ┌────────────────┐  PUBACK   ┌──────────────┐
 │ GPIO producer │────────▶ │  durable queue │ ────────▶ │  MQTT client │──▶ broker
 │  (pins 17/27/ │  (write  │   (SQLite/WAL) │  (read+   │  (own thread)│◀── broker
 │   22/5)       │  at      └────────────────┘   delete) └──────┬───────┘
 └───────────────┘  capture                                     │ cmd (validated)
        ▲                                                       ▼
        │                                              ┌──────────────────┐
        └────────────── applies config/pin ◀────────── │  control thread  │
                        (never the MQTT thread)         └──────────────────┘
✖ Hard rules for the MQTT thread It must never access GPIO, never run machine/flow logic, and never mutate state directly. Inbound commands are validated and handed to the control thread via a queue; the control thread is the only code that touches hardware. A malformed or malicious command therefore cannot drive a relay from the network path.

OS tuning (the real limit)

  • File descriptors: LimitNOFILE=65535 (systemd) / ulimit -n — one FD per connection plus headroom.
  • net.core.somaxconn, net.ipv4.tcp_max_syn_backlog raised to survive the reconnect storm.
  • fs.file-max comfortably above the FD ceiling.
ℹ Capacity reality check 500 devices with sparse events and a 60 s keepalive is a light load for a single modern Mosquitto node (it handles tens of thousands of connections on modest hardware). Plan capacity around availability and reconnect bursts, not steady-state throughput — which is exactly why §2's HA decision matters more than any tuning knob here.

15 — Migration path (500 devices can't flip at once)

  1. Phase 0 — Stand up. Deploy Mosquitto (+HA), the backend consumer with idempotent upserts, a cert/provisioning pipeline, and monitoring ($SYS + presence).
  2. Phase 1 — Dual-write. New firmware publishes to MQTT and keeps calling REST. Server dedups; you compare the two streams for parity on a pilot group (say 10–20 units).
  3. Phase 2 — Cut reads over. Make MQTT the source of truth for reporting/dashboards; REST stays as a fallback. Roll firmware fleet-wide in waves via cmd/ota.
  4. Phase 3 — Retire REST. Once all units report healthy on MQTT, decommission the REST endpoints and the polling heartbeat.

Dual-run is not optional at this scale — it's how you avoid a fleet-wide outage during cutover and how you prove the new path before trusting it.

16 — Assumptions & open decisions

Locked (say if you want them changed)

  • MQTT 5.0 (needed for native request/response).
  • Hybrid OTA: URL + hash over MQTT, ZIP over HTTPS.
  • QoS 1 + app-layer idempotency (not QoS 2).
  • Per-device identity is mandatory.

Still yours to decide

  • Auth mechanism: mTLS (recommended) vs DB-backed username/password. Drives the provisioning pipeline.
  • HA topology: Mosquitto active/passive failover vs migrating to a clustering broker (EMQX/VerneMQ/HiveMQ). Same contract either way.
  • company slug: how the current login email maps to a stable company topic segment.
  • Keep password login at all? With mTLS, req/login can disappear entirely.
  • Config source of truth: keep unitsetup.ini locally, or make cmd/config (retained) authoritative.
