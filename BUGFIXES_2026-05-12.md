# Bug Fixes — 2026-05-12

> Phase 4b user management regressions. All six root causes documented before code was touched.

---

## Bug 1 — Login throttled with "too-many-login-attempts"

**Root cause:**
`backend/src/middleware/rateLimiter.js` defines `loginRateLimiter` with `max: 5` hardcoded — it never reads the `THROTTLE_AUTH_LIMIT` env var. `.env.local` has `THROTTLE_AUTH_LIMIT=5`, matching the spec, but the code ignores it. In dev, 5 attempts are exhausted quickly during iterative testing (page refresh + form submit cycles), and the counter never resets after a successful login, so you're blocked for the full 60-second window even after you get the password right.

**Fixes applied:**
1. `rateLimiter.js` now reads `THROTTLE_AUTH_LIMIT` from env (default: 5).
2. `.env.local` sets `THROTTLE_AUTH_LIMIT=50` for dev (documented in `.env.example`).
3. On a 200 from `POST /auth/login`, `auth.routes.js` calls `loginRateLimiter.resetKey(ip)` to clear the bucket (express-rate-limit ≥5 exposes this via the store).

**Regression test:** `test/auth-throttle.test.js` — 5 bad logins → 429; one good login → 200 + reset; 5 more bad logins → no 429 yet.

## Bug 2 — Two "All Users" buttons

**Root cause:**
`frontend/src/app/(admin)/admin/access/users/page.tsx` has two places that both render an "All Users" button:
1. `HeaderButtons` component (line 133–139) — a top-right button with `onClick={() => {}}` (no-op).
2. The sub-tabs row (lines 332–337 / 536–540) — another "All Users" button that represents the active filter.

The agent ported both the legacy split-button dropdown trigger AND the tabs row, resulting in a duplicate.

**Fix applied:**
Removed "All Users" from `HeaderButtons`. The component now only renders "+ Add New" and "Create Company". The tab row is the sole mechanism for the All/Deactivated/Deleted filter.

## Bug 3 — "Deactivated Users" navigates away instead of filtering in-place

**Root causes:**
1. The sub-tab buttons call `router.push('/admin/access/users/deactivated')` — a separate route.
2. `/admin/access/users/deactivated/page.tsx` guards with `if (tenantId === null) return <Text>Pick a tenant…</Text>`. Super Admin always has `tenantId: null` (global view), so they always hit this guard and see the wrong empty state.

**Fixes applied:**
- `users/page.tsx` now reads `useSearchParams()` for a `status` param (`active` / `deactivated` / `deleted`, default `active`) and renders the appropriate table inline.
- Tab buttons update the URL with `router.push('?status=deactivated')` etc. — back/forward navigation works.
- The separate `deactivated/page.tsx` and `deleted/page.tsx` files are replaced with redirect stubs to the canonical URL so any existing links still work.
- Removed the wrong "Pick a tenant" copy; empty-state now shows "No deactivated users found."

## Bug 4 — Action buttons broken

**View button root cause:**
Both the View (eye icon) and Edit (pencil icon) buttons call `onEdit()` which opens `UserFormModal`. No separate detail page exists. The View button is a pure alias for Edit.

**Deactivate / Delete root cause (global SuperAdmin view):**
In `GlobalUsersTable`, scope is `{ tenantId: null, isAdmin: true }`. `tenantHeaders(null, true)` returns `undefined` (no `X-Tenant-Id` header sent). The backend's `tenantMiddleware` rejects all mutating requests with `400 no-tenant-context`. Deactivate and delete calls silently fail (the error toast shows, but the UI looks broken because there's no API call succeeding).

**Fixes applied:**
- View button now navigates to `/admin/access/users/[id]` detail page (built as a new file).
- `useToggleAdminUserStatus` and `useDeleteAdminUser` now accept an optional per-call `tenantId` override in the mutationFn argument.
- `GlobalUsersTable` action handlers pass `row.companyId` as the tenant override so the correct `X-Tenant-Id` header is sent.
- Detail page (`/admin/access/users/[id]/page.tsx`) shows AntD Descriptions with all user fields, action buttons (Edit, Deactivate/Activate, Resend Confirmation, Delete), and a "Not confirmed" warning banner when applicable.

## Bug 5 — No confirmation email when Super Admin creates a company

**Root causes:**
1. `admin-users.service.js` `create()` defaults `confirmed: dto.confirmed ?? true` — new users are marked confirmed by default, so no confirmation email is ever needed.
2. `resendConfirmation()` generates a code and stores it, but returns `{ ok: true, queued: false }` — no email is ever sent.
3. `auth.service.js` `login()` only checks `user.status !== 1`, never checks `user.confirmed` — unconfirmed users can log in freely.
4. No `GET /api/v1/auth/confirm/:token` route exists.
5. No nodemailer package installed.
6. No frontend confirmation page.

**Fixes applied:**
- `nodemailer` added to backend dependencies.
- `backend/src/services/mail.service.js` created — thin wrapper around nodemailer using `MAIL_HOST/PORT/USER/PASS/FROM` env vars (MailHog in dev).
- `create()` now respects `dto.sendConfirmationEmail` — if `true` and `dto.confirmed` is falsy, stores a `crypto.randomUUID()` confirmation code and queues a confirmation email (inline async, no BullMQ for now — BullMQ setup is a separate concern).
- `login()` now returns `403 { error: 'account_not_confirmed' }` when `user.confirmed === false`.
- `GET /api/v1/auth/confirm/:token` route added to `auth.routes.js` — looks up user by `confirmationCode`, flips `confirmed=true`, clears the code.
- `POST /api/v1/auth/confirm/resend` route added — accepts `{ email }`, re-issues a code and resends the email.
- Frontend: `app/(public)/account/confirm/[token]/page.tsx` built.
- Login page now catches the `account_not_confirmed` 403 and shows the unconfirmed message with a resend link.

## Bug 6 — Stuck in impersonated user; no way back to Super Admin

**Root cause:**
`ImpersonationBanner` is mounted only in `AdminShell` (line 488 of `AdminShell.tsx`). After `POST /admin/users/:id/impersonate`, the code calls `router.push('/dashboard')`. The `/dashboard` route is under `(user)/layout.tsx → UserShell`. `UserShell` renders `MarketingHeader` + `MarketingFooter` only — it has NO `ImpersonationBanner`. So the banner is literally absent from every page the impersonated session visits.

All the underlying mechanics are correct:
- JWT carries `impersonator_id` claim (auth.service.js line 76).
- `/me` returns `impersonatorId` + `impersonator` object (me.routes.js lines 33–45).
- `POST /auth/impersonate/stop` is in `auth.routes.js` and works correctly.
- `ImpersonationBanner.tsx` renders correctly when `me.impersonatorId` is present.

The only missing piece was that `UserShell` never rendered the banner.

**Fix applied:**
Added `<ImpersonationBanner />` to `UserShell`, between the `MarketingHeader` and `Content`. The banner component is self-hiding when `me.impersonatorId` is null, so it costs nothing when not impersonating.
